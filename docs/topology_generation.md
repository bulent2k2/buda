# Topology Generation Design

This document covers how BUDA generates routing topology candidates for a bundle (stage 2) and how the planner selects one (stage 3).

---

## Overview

A **topology** is an ordered list of axis-aligned segments connecting one source block to one or more destination blocks. Topologies are generated exhaustively per bundle — every plausible shape is a candidate — and the planner picks one based on congestion and span cost.

All geometry is integer Manhattan. Segments carry a `layer_hint` (overridden by the planner). The candidate set for a bundle is sorted by estimated wirelength before the planner sees it.

---

## Busterm Mode and Corner Margins

The generator operates in **busterm mode** by default. In this mode, segment endpoints land on block *faces* rather than block centres. Each block's bounding box is inset by its `BlockCornerMargin{dx, dy}` at Busterm construction time:

```
Busterm.bbox = block_rect.shrink(dx, dy)
```

`dy` constrains the Y range on left/right (vertical) faces; `dx` constrains the X range on top/bottom (horizontal) faces. The guard in `Rect::shrink` prevents inversion when the margin exceeds half the face extent. All shape functions operate on `bbox` directly — the margin is invisible to them.

The Hanan grid used for Z/U trunk placement is also built from the shrunken bboxes, so trunk and stub positions automatically respect the margin.

Busterm mode can be disabled per generator instance (`set_busterm_mode(false)`), which reverts to centre-to-centre routing. The `.buda` command flag is `center_mode`.

## 2-Pin Topologies

Generated by `generate_candidates(src, dst)`.

### I-shapes (degenerate, busterm mode only)

When the margin-inset bboxes overlap in one axis, a straight single-segment wire is possible:

- **I_V**: blocks overlap in X → vertical segment through the overlap midpoint, endpoints on the opposing Y faces.
- **I_H**: blocks overlap in Y → horizontal segment through the overlap midpoint, endpoints on the opposing X faces.

I-shapes are the shortest possible topology and are always preferred if geometrically feasible.

### L-shapes

Two segments with one bend. Generated by `add_l_shapes`.

**L_HV** — horizontal first, then vertical:

```
src ──────┐
          │
         dst
```

The horizontal segment departs from the src face nearest dst (`src.face_x(d.x)`). The bend lands on the dst face (`dst.face_x(sx)`). In busterm mode two independent variants are generated:

- **Option 1**: H segment at `src.y2` (top face), V drops to `dst.y1` — used when src is below dst.
- **Option 2**: H segment at `src.y1` (bottom face), V rises to `dst.y2` — used when src is above dst.

When the X ranges overlap (the bend would collapse), the H is routed into whichever exclusive X zone of dst exists.

**L_VH** — vertical first, then horizontal. Symmetric to L_HV with roles of X and Y swapped. Also generates two variants (A: stub down from src bottom, B: stub up from src top).

### Z-shapes

Three segments: stub from src, vertical or horizontal trunk, stub to dst. Generated by `add_z_shapes`. The trunk is placed at a Hanan grid channel midpoint strictly between the two block centres, ensuring both stubs are non-degenerate.

**Z_HVH** — H stub · V trunk · H stub:

```
src ────┐
        │  ← trunk at x_cut (Hanan channel midpoint)
        └──── dst
```

For each valid `x_cut`:
- `sx = src.face_x(x_cut)` — where H stub meets src face
- `dx = dst.face_x(x_cut)` — where H stub meets dst face
- `ty_src = stub_y(src, toward=d.y)` — Y level of src H stub
- `ty_dst = stub_y(dst, toward=s.y)` — Y level of dst H stub

When both stubs land at the same Y (blocks are Y-aligned), the V trunk collapses. A **spread variant** is generated instead: the two H segments are forced to `src.y1` / `src.y2` (opposite corners) and each is extended slightly past the trunk so their spans overlap. This guarantees NUTS places them on distinct tracks.

**Z_VHV** — V stub · H trunk · V stub. Symmetric with X and Y roles swapped.

### U-shapes

Three segments routed *outside* the bounding box of the two blocks. Used when a straight path would cross congestion. Generated by `add_u_shapes`. The trunk is placed at Hanan channel midpoints that lie outside the `[min_centre, max_centre]` interval, i.e. to the left/right of both blocks (U_HVH) or above/below both (U_VHV).

**U_HVH** — H stub · V trunk · H stub, trunk outside in X:

```
        ┌─── trunk at x_cut < min_x  (left detour)
src ────┘        or x_cut > max_x  (right detour)
dst ────┘
```

**U_VHV** — V stub · H trunk · V stub, trunk outside in Y.

The outer channel positions are set to one channel-width (10% of the bbox span) beyond the extreme Hanan line, ensuring the trunk is clearly outside.

### UU-shapes (double detour, optional)

Enabled by `set_double_detour(true)` / the `.buda` flag `double_detour`. Generated by `add_uu_shapes`. Adds a second L-turn at the src side so the src stub exits a *side* face rather than the primary face. Useful in high-congestion areas where the normal U path is blocked.

**UU_VHV** — src exits an X-face, then routes to the H trunk:
```
src ──┐         ← H exit from src side face
      │         ← V to trunk level
      └──────── dst
                ← trunk at y_cut OOB
```

**UU_HVH** — symmetric: src exits a Y-face, then routes to the V trunk.

UU shapes only produce candidates when the exit face exits the block-pair bounding box, and require at least 3 segments.

## Multi-Pin Topologies

Generated by `generate_multicast_candidates(src, dst_names)`.

### I-shapes (degenerate)

If all pin centres share an X or Y coordinate, a single segment connects all of them. These are returned immediately without further candidates.

### Single-trunk (H or V spine + stubs)

The workhouse for 1-driver / N-receiver nets. Generated by `add_trunk_h` and `add_trunk_v`.

**H-trunk (TRUNK_H)**:

```
      ┌─── dst_0
──────┼─── dst_1  ← spine at y_trunk
      └─── dst_2
src ──┘
```

The spine is a single H segment spanning all attachment points. Each pin that does not lie on the spine gets a V stub. Blocks whose original (unshrunken) bbox contains `y_trunk` are **pass-throughs** — their spine endpoint snaps to the block face, no stub is generated.

Spine endpoint optimisation (busterm mode):
1. **Pass-through snap**: if all stubs are on one side, `y_trunk` is snapped to the extreme of the pass-through block's bbox on that side, minimising average stub length.
2. **Extreme stub slide**: the leftmost and rightmost stubbed blocks slide their attachment X toward the spine centre (to `block.bbox.x2` / `block.bbox.x1` respectively), shortening the spine.
3. **Post-slide pull-to-face**: if sliding exposed a pass-through block at a new extreme, it is re-snapped to its face.

**V-trunk (TRUNK_V)**: symmetric in X/Y.

**OOB trunks**: trunk positions outside the pin bounding box are also generated (`TRUNK_H_OOB`, `TRUNK_V_OOB`). These serve the same role as U-shapes in 2-pin routing — a detour around congestion. OOB positions are the midpoints of Hanan intervals outside the pin bbox, plus one extra step at 10% of the Hanan extent beyond each extreme Hanan line.

### MST topologies

Generated by `add_mst_candidates`. Runs Prim's algorithm (`compute_mst`) on all block bboxes using minimum Manhattan distance (`closest_points`) as edge weight. The resulting spanning tree is laid out as a series of L-bends, with two variants:

- **MST_HV**: each L-bend goes horizontal first, then vertical.
- **MST_VH**: each L-bend goes vertical first, then horizontal.

MST candidates tend to have lower total wirelength than a single-trunk topology when the pins are geometrically scattered, at the cost of more segments and potential via congestion.

**Relay-hub completion (opt-in `spine_relays`).** At a high-degree MST hub (a block where ≥3 tree edges meet) the incident stubs are joined, by default, with an over-the-cell *bracket chain* — several connector segments that make the join physically real. The `spine_relays` flag (default off; also the `set_spine_relays(true)` API and the `BUDA_SPINE_RELAYS=1` env) replaces that chain with a single **collector spine**: one segment perpendicular to the stubs that each stub taps at its own coordinate (independent NUTS slide), collapsing the connector count (measured −61% on `big.buda`'s pure-MST hubs). Opt-in / byte-identical when off; measured net-positive on electrical-correctness (`viol_bundles`) but with a couple of raw-metric regressions, so it stays off by default. See the flag semantics in the [BUDA Script reference](script_reference/topologies.md) and the design notes in `docs/internal/wishlist/wishlist-topo.md`.

### Bi-trunk (BITRUNK_H)

Generated by `add_multi_trunk_candidates` for nets with **4+ receivers**.

Two parallel H spines are placed at the 25th and 75th percentile Y coordinates of the pin set. A vertical backbone connects them at the X midpoint. Each pin is assigned to whichever trunk is closer in Y, and gets a V stub to that trunk.

```
   ──────────────  ← y_t1 (25th pct trunk)
         │         ← vertical backbone
   ──────────────  ← y_t2 (75th pct trunk)
```

This is a heuristic for wide fanout where a single trunk would produce very long stubs on extreme receivers.

## Candidate Assembly and Filtering

After all shapes are generated:

1. **`annotate_endpoints`**: for each segment endpoint that lies on a block face, records the corresponding `Busterm` in `Topology::seg_busterms`. Used by `ConnTopology` to identify busterm connections without a full geometric scan.

2. **`annotate_and_sort`**: computes `estimated_wirelength` for each topology (sum of segment Manhattan lengths) and sorts ascending. The planner sees shortest-first.

3. **`filter_pinched`**: builds a `ConnTopology` for each candidate and discards any topology where a segment's perpendicular slide range is a single point (`perp_lo == perp_hi`). A pinched segment has no room for NUTS to place it without violating an interval constraint — the topology is structurally infeasible.

## Topology Selection (Stage 3)

Selection is performed by `GlobalRouter::optimize_topologies`.

### Congestion model

The floorplan is overlaid with a **Hanan grid**. Each pair of adjacent grid lines defines a *channel*. For each channel, a `GlobalCut` tracks per-band capacity and usage. Capacity is proportional to the available routing length in a band minus block obstruction, divided by the effective bus width (raw width × dilution factor for power-grid overhead on that layer).

### Scoring

Each segment is scored independently with three additive terms:

```
score = cong_cost + span_cost + base_cost_non_top
```

- **`cong_cost`**: hyperbolic `u / (1 - u)` where `u` is the band utilisation after placing this segment. Approaches infinity as the band fills, enforcing hard congestion avoidance.
- **`span_cost`**: penalty when the segment's span falls outside the layer's configured `[span_min, span_max]` window, weighted by `kSpan`. Guides long segments to higher metal and short stubs to lower metal.
- **`base_cost_non_top`**: flat penalty for using a non-`TOP` layer, weighted by `base_cost_non_top` (default 0.1). Keeps the default preference on top layers without hard-blocking lower ones.

A topology's score is the **maximum segment score** across all its segments (weakest-link).

### Optimisation loop

Bundles are processed **widest first** (fattest-bus-first greedy). For each bundle:

1. Snapshot the current cut state.
2. For each topology candidate (or only the pinned one if `topology_pinned`):
   - For each segment, independently select the layer (from the direction-appropriate set, highest ID first for tie-breaking) that minimises `cong + span + base`.
   - Apply each segment choice to the running cut state so within-topology congestion interactions are captured.
   - Record the topology score as the max segment score.
   - Roll back to the snapshot before scoring the next candidate.
3. Select the candidate with the lowest score. Ties broken by lowest candidate index (shortest wirelength, since candidates are sorted).
4. Commit the winning topology's per-segment layer choices permanently to the cut state, so subsequent bundles see the correct congestion.

### Topology pinning

If a user has selected a topology in the `TopologyExplorer` and saved to the sidecar JSON, `_apply_selections()` sets `topology_pinned = true` and `selected_topology_index` on the wrapper before `optimize_topologies` runs. The planner scores only that one candidate and skips the search, but still runs the per-segment layer assignment — so layer decisions are always consistent with the selected topology's actual segment directions.

## Topology Type String Reference

| Type | Shape | Pins | Segments |
|---|---|---|---|
| `I_H` | Straight horizontal | 2+ | 1 |
| `I_V` | Straight vertical | 2+ | 1 |
| `L_HV@x{bend}@y{hy}` | H then V | 2 | 2 |
| `L_VH@y{bend}@x{vx}` | V then H | 2 | 2 |
| `Z_HVH@x{cut}@y{ty}` | H · V trunk · H | 2 | 2–3 |
| `Z_VHV@y{cut}@x{vx}` | V · H trunk · V | 2 | 2–3 |
| `U_HVH@x{cut}` | H · V trunk (OOB in X) · H | 2 | 2–3 |
| `U_VHV@y{cut}` | V · H trunk (OOB in Y) · V | 2 | 2–3 |
| `UU_VHV@y{cut}` | H+V L-exit from src · H trunk · V | 2 | 3–4 |
| `UU_HVH@x{cut}` | V+H L-exit from src · V trunk · H | 2 | 3–4 |
| `TRUNK_H@y{trunk}` | H spine + V stubs | 2+ | 1 + stubs |
| `TRUNK_V@x{trunk}` | V spine + H stubs | 2+ | 1 + stubs |
| `TRUNK_H_OOB@y{trunk}` | H spine OOB + V stubs | 2+ | 1 + stubs |
| `TRUNK_V_OOB@x{trunk}` | V spine OOB + H stubs | 2+ | 1 + stubs |
| `MST_HV` | Prim MST, L-bends H-first | 2+ | varies |
| `MST_VH` | Prim MST, L-bends V-first | 2+ | varies |
| `BITRUNK_H` | 2 H spines + V backbone + V stubs | 4+ | 3 + stubs |
